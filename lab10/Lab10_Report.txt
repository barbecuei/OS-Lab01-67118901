1. The Role of the Operating System:

File System & Permissions (Lab 9):

จากการทดลอง ultimate_cluster_os.py ผมสังเกตว่าโปรแกรมใช้คำสั่ง os.path.exists(dataset_path) เพื่อตรวจสอบว่าไฟล์ Dataset มีอยู่หรือไม่ก่อนเริ่มทำงาน เมื่อ Workload D พยายามใช้ไฟล์ secret_keys.txt ที่ไม่มีอยู่ ระบบจึงปฏิเสธงานและแสดงข้อความว่าไม่พบไฟล์
ผมเข้าใจว่าการตรวจสอบไฟล์ก่อนเริ่มงานช่วยป้องกันข้อผิดพลาดในการเข้าถึงข้อมูล แต่ในการทดลองนี้โปรแกรมตรวจสอบเพียงการมีอยู่ของไฟล์ ยังไม่ได้ตรวจสอบ Permissions ทั้งหมดเหมือนที่ทดลองใน Lab 9

Memory Management (Labs 5/6):

โปรแกรมใช้ while loop ร่วมกับ ram_lock เพื่อตรวจสอบ RAM ที่เหลือก่อนจัดสรรให้แต่ละ Workload หาก RAM ไม่เพียงพอ งานจะรอจนกว่าจะมี RAM ว่าง แทนที่จะเริ่มทำงานทันที
จากผลการทดลอง Workload A ใช้ RAM 40 GB, Workload B ใช้ 16 GB และ Workload C ใช้ 2 GB รวมเป็น 58 GB จากทั้งหมด 64 GB ทำให้ระบบยังเหลือ RAM 6 GB และสามารถทำงานทั้งสามงานพร้อมกันได้
ผมเข้าใจว่าการจัดสรร RAM ตามขีดจำกัดช่วยลดความเสี่ยงที่ระบบจะใช้หน่วยความจำเกินกำลัง ซึ่งอาจทำให้เกิดการสลับ Page ไปยังดิสก์บ่อย ๆ และนำไปสู่ Thrashing

Concurrency & Deadlocks (Labs 3/4):

โปรแกรมใช้ sorted(req_gpus) เพื่อเรียงหมายเลข GPU ก่อนขอ Lock ทำให้ทุก Workload ขอทรัพยากรตามลำดับเดียวกัน เช่น Workload A ที่ต้องการ GPU [2, 1, 0] จะถูกเรียงเป็น [0, 1, 2] ก่อนเริ่มขอ Lock
ผมเข้าใจว่าการกำหนดลำดับการขอทรัพยากรแบบเดียวกันช่วยป้องกัน Circular Wait เพราะแต่ละงานจะไม่ขอ GPU ย้อนกลับไปยังหมายเลขที่ต่ำกว่าในขณะที่ถือ Lock ของ GPU หมายเลขสูงกว่าอยู่ จึงช่วยลดความเสี่ยงของ Deadlock


2. Hardware Utilization:

จากการทดลอง ผมสังเกตว่าระบบสามารถรัน Workload A, B และ C พร้อมกันได้ โดย Live Dashboard แสดง Active Jobs เท่ากับ 3 และ RAM เหลือ 6 GB จากทั้งหมด 64 GB
Workload A ใช้ RAM 40 GB และ GPU 0, 1, 2 สำหรับ Training ส่วน Workload B ใช้ RAM 16 GB และทำงานแบบ CPU-only โดยไม่ต้องใช้ GPU จึงสามารถทำงานพร้อมกับ Workload A ได้ ขณะที่ Workload C ใช้ RAM 2 GB และ GPU 3 ซึ่งยังว่างอยู่สำหรับ Inference
ผมเข้าใจว่าทั้งสามงานสามารถทำงานพร้อมกันได้ เพราะระบบตรวจสอบ RAM ก่อนจัดสรร และใช้ GPU Locks เพื่อป้องกันไม่ให้งานต่าง ๆ ใช้ GPU ตัวเดียวกันในเวลาเดียวกัน อีกทั้งโปรแกรมยังใช้ Worker Threads แยกการทำงานของแต่ละ Workload ออกจากกัน
เมื่อแต่ละงานทำงานเสร็จ ระบบจะคืน RAM และปลด GPU Locks โดยจากผลการทดลอง Workload C เสร็จก่อน ตามด้วย Workload B และ Workload A หลังจากทุกงานเสร็จ Live Dashboard แสดง RAM กลับมาเป็น 64 GB และ GPU ทั้ง 4 ตัวเป็น IDLE
จากผลนี้ผมเห็นว่าการจัดการทรัพยากรที่เหมาะสมช่วยให้งาน AI หลายประเภทใช้ Hardware ร่วมกันได้โดยไม่จำเป็นต้องรอให้งานก่อนหน้าทำงานเสร็จทั้งหมด


3. Course Reflection (AI Engineering Context):

จากการเรียนและทดลองในรายวิชา Operating Systems ผมเข้าใจว่าการเป็น MLOps Engineer ไม่ใช่แค่การเขียน Python หรือ PyTorch เพื่อสร้างและเทรนโมเดล AI เท่านั้น แต่ต้องเข้าใจด้วยว่าระบบปฏิบัติการจัดการทรัพยากรอย่างไร เพื่อให้โมเดลสามารถทำงานได้อย่างมีประสิทธิภาพ
ความรู้เรื่อง Memory Management ช่วยให้ผมวิเคราะห์ปัญหา RAM ไม่เพียงพอและ Thrashing ได้ ส่วน CPU Scheduling และ Process Queues ช่วยให้เข้าใจการจัดการงานหลายงานพร้อมกัน ขณะที่ File Systems และ Permissions ช่วยป้องกันไฟล์โมเดลสำคัญจากการเข้าถึงหรือแก้ไขโดยไม่ได้รับอนุญาต และ Deadlock Avoidance ช่วยลดปัญหาการแย่งใช้ทรัพยากรในระบบที่มี GPU หลายตัว
จากการทดลอง AI Cluster OS ผมเห็นว่าการจัดสรรและคืนทรัพยากรอย่างเหมาะสมช่วยให้งาน Training, Preprocessing และ Inference ทำงานพร้อมกันได้ ผมจึงคิดว่าความรู้ OS Internals จะช่วยให้ผมสามารถวิเคราะห์และแก้ไขปัญหาด้านประสิทธิภาพ ความปลอดภัย และการใช้ทรัพยากรของระบบ AI ได้ดีกว่าการรู้เพียงวิธีเขียนโค้ดให้โปรแกรมทำงานสำเร็จ
